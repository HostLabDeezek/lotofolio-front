Bienvenue sur Lotofolio

Guide rapide pour explorer le projet en 5 minutes

Bonjour, et merci de prendre le temps de regarder mon travail. Avant de plonger dans Lotofolio, sachez que j'ai également un second projet en React / Node que vous pouvez consulter ici : technopark-front-ten.vercel.app . Bienvenue sur Lotofolio ! J'ai créé cette application full-stack (Angular / Node.js) pour vous offrir un aperçu concret de mes compétences. C'est un projet de maintien à niveau et de formation continue qui me permet d'appliquer les meilleures pratiques de développement — il illustre mon engagement professionnel : fournir un code propre, structuré et maintenable, du back-end jusqu'à l'interface utilisateur.

J'en ai réalisé l'intégralité du développement. L'interface est conçue avec Angular (système moderne de Signals), tandis que la logique métier et la base de données s'appuient sur Node.js et PostgreSQL. J'aborde ce projet avec la même rigueur qu'en entreprise : sécurité et stabilité passent avant tout. Au-delà de la base technique (authentification, structure des données, architecture front/back), le cœur du jeu est désormais jouable de bout en bout : côté back, les tirages sont planifiés, le tirage courant est exposé et les grilles validées ; côté front, vous pouvez composer jusqu'à cinq grilles (à la main ou en flash), les soumettre, puis consulter l'historique complet de vos parties avec le classement de vos grilles. Le tout est couvert par des tests automatisés, front et back.

info

À savoir avant de commencer

Le back est hébergé sur le plan gratuit de Render, qui met le serveur en veille après ~15 minutes d'inactivité. La première requête peut prendre 30 à 60 secondes (cold start), ensuite tout est instantané. Si la page de connexion semble figée au premier essai, laissez-lui ce petit délai.

Côté périmètre, en plus de /auth et GET /jeux, le moteur de jeu est maintenant exposé côté API : GET /jeux/:id/current-tirage (tirage du jour jouable), POST /parties (validation d'une ou plusieurs grilles), GET /parties/history (historique des parties) et GET /parties/:id (détail d'une partie). Les écrans front correspondants sont désormais en place : voir le parcours ci-dessous.

Parcours pas-à-pas

Voici ce que vous pouvez faire aujourd'hui pour valider le bon fonctionnement de l'application telle qu'elle est à ce stade :

Cliquez sur « Connexion », saisissez les credentials du compte de démo ci-dessus. Le back renvoie un JWT qui est stocké en localStorage. Toutes les requêtes suivantes ajoutent automatiquement l'en-tête Authorization: Bearer … via un HTTP interceptor.

Une fois loggué, vous arrivez sur la page d'accueil protégée par un authGuard. Le composant déclenche JeuStore.loadJeux() — un signal store @ngrx/signals qui charge la liste des jeux et expose loading, error et jeux en signaux réactifs.

Depuis la liste, ouvrez un jeu : la page de grille charge le tirage du jour (GET /jeux/:id/current-tirage) et vous laisse composer jusqu'à cinq grilles à la fois. Chaque grille se remplit à la main (numéros + numéro chance, dans les quotas du jeu) ou via le Flash : un tirage aléatoire révélé avec une petite animation, pour 1 à 5 grilles d'un coup. Quand tout est complet, « Valider » envoie l'ensemble en une seule requête POST /parties ; un toast confirme l'enregistrement et la page se réinitialise.

La saisie respecte la fenêtre de fermeture du back : une horloge locale affiche l'heure limite (ex. « jusqu'à 19h54 ») puis un compte à rebours dans la dernière heure ; passé le cutoff, la composition se verrouille et bascule automatiquement sur le tirage suivant dès qu'il est créé. Les erreurs métier du back (grille invalide, doublon, cutoff dépassé…) sont remontées en messages clairs en tête de page.

Cliquez sur Mon historique dans le header. La page charge l'ensemble de vos parties via GET /parties/history et les affiche triées par date décroissante. Chaque ligne est un bouton qui ouvre le détail de la partie (GET /parties/:id).

Sur la page de détail, vous voyez le tirage gagnant (boules bleues / chance dorée) et vos grilles classées par nombre de numéros correspondants. Les numéros matchés sont mis en évidence en vert, les numéros chance en ambre. Un contrôle + / − permet d'ajuster le nombre de grilles affichées. Tout est piloté par des computed() Angular Signals en OnPush — aucun recalcul inutile.

Côté utilisateur

person Ce que voit un utilisateur connecté

L'utilisateur connecté accède au header (nom + bouton de déconnexion) et à la liste des jeux disponibles. Chaque jeu mène à sa page de grille, où il compose et valide ses grilles (voir l'étape 3). Le header expose également Mon historique : la liste de toutes ses parties jouées, et pour chacune le détail du tirage gagnant avec ses grilles classées par score (voir l'étape 4). Le bouton de déconnexion purge le token, vide le signal user du AuthService et redirige vers /login. Toute requête HTTP qui revient en 401 (token expiré, par exemple) déclenche le même flux automatiquement via l'authInterceptor.

Pour aller plus loin (optionnel)

Ouvrez l'onglet Réseau, faites une action quelconque. Vous verrez l'en-tête Authorization: Bearer … ajouté automatiquement sur toutes les requêtes vers l'API. Si vous supprimez le token de localStorage et faites une requête, l'errorInterceptor normalise le message et l'authInterceptor vous redirige vers /login.

Faites 6 tentatives de login en moins de 15 minutes avec un mauvais mot de passe. La 6ᵉ renvoie un HTTP 429. Le rate-limit est ciblé uniquement sur /auth/login (5 / 15 min) et /auth/register (3 / heure) — pas un rate-limit global naïf qui pénaliserait les vraies requêtes.

Points techniques à noter

Front (Angular 21)

  • Angular 21 standalone partout (zéro NgModule), inject() au lieu des constructeurs DI.
  • Signals + @ngrx/signals pour le state global (JeuStore) — modèle réactif moderne, fini les Observables passés aux async pipe.
  • Auth JWT : AuthService avec un signal user, garde de route authGuard sur l'arbre protégé.
  • Deux HTTP interceptors : authInterceptor (Bearer auto + auto-logout sur 401) et errorInterceptor qui normalise toute erreur API en une ApiError unique (status + code + message + détails), mappée en messages utilisateur côté écran.
  • Page de jeu en signaux dérivés : composition multi-grilles, flash animé, fenêtre de cutoff et compte à rebours pilotés par des computed() en OnPush ; l'horloge tourne runOutsideAngular pour ne pas gêner la stabilisation (tests / SSR).
  • Notifications éphémères via un ToastService signal (pile de toasts auto-dismiss, sans dépendance DOM) monté une fois dans le Layout.
  • SSR-safe : tous les accès localStorage sont protégés par isPlatformBrowser(PLATFORM_ID), l'app peut tourner en Angular SSR sans planter au render initial.
  • TypeScript strict + strictTemplates activés — pas de any implicite, les erreurs de type dans les templates cassent le build.
  • Material 3 avec theming via mat.theme() et CSS variables système (var(--mat-sys-…)) plutôt que des couleurs en dur.

Back

  • Node 20 + Express 5 + TypeScript strict (ESM natif), Prisma 7 + PostgreSQL 16.
  • Validation des variables d'env au démarrage avec Zod : le process refuse de booter si JWT_SECRET < 32 chars ou si DATABASE_URL est invalide. Fail fast plutôt qu'API mal configurée en prod.
  • Liveness /health vs readiness /ready : seul /ready tape la BDD (SELECT 1), évite les redémarrages intempestifs sur un hoquet réseau Postgres.
  • Rate-limit ciblé par endpoint sensible (5 logins / 15 min, 3 registers / heure) au lieu d'un rate-limit global.
  • CORS en whitelist explicite lue depuis l'env (multi-origines via ,), helmet, mots de passe hashés en bcrypt 10 rounds.
  • Graceful shutdown sur SIGINT / SIGTERM avec prisma.$disconnect() et timeout 10 s — important pour les déploiements zero-downtime sur Render.
  • Infra as Code via render.yaml : déploiement reproductible, JWT_SECRET généré côté Render, jamais en clair.
  • Logs structurés Winston (JSON en prod, coloré en dev).
  • Validation Zod par route, format d'erreur standardisé {{ '{' }} error, details? {{ '}' }}.

Limites assumées

  • Pas de refresh token (JWT 7 jours unique, pas de révocation côté serveur).
  • RBAC pas encore actif (enum Role prêt en base, middleware à venir).
  • Pas de CI de tests/build (seul un workflow de revue automatisée est branché).
